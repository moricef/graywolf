Remote Actions

Send Actions and authenticated CA2RXU control commands from inside Messages

Controlling an RXT / CA2RXU iGate? Go directly to Send an authenticated iGate command. That procedure uses the iGate’s shared key. The TOTP credentials and macros described below belong to Graywolf Actions.

A Remote Action is the outbound side of the same grammar described on the Actions page. Where Actions defines what your station will run when an @@-prefixed message arrives, Remote Actions lets you send those messages at someone else’s station from inside Messages — either by tapping a saved macro tile or by typing a one-off command.

For the TOTP Actions workflow, both sides have to be set up. The receiving station must already have a matching Action defined; this page covers the sender side and walks through the credential copy-paste between the two.

Two sides, one secret

OTP-protected Actions use a shared Secret Key — the standard RFC 4648 base32 string a TOTP authenticator app consumes. The receiving station generates that Secret Key when the operator creates the credential on its Actions page; the sending station stores the same Secret Key in the Remote Actions drawer. From then on, both sides compute the same six-digit code from the wall clock and the receiver accepts it.

There is no key exchange protocol — operators copy and paste the Secret Key over a side channel they trust (signal, email, voice over the air, paper handoff). Treat it like an SSH key.

Same string, two sides. The value labelled Secret Key in the receiver’s reveal panel and the value labelled Secret Key in the sender’s New Secret dialog are the same string. If you mistype one character, every fire returns bad_otp.

Setting up the credential — receiver side

On the receiving station (the one whose action you want to fire):

  1. Open Actions in the sidebar.
  2. In the OTP Credentials table, click + New Credential.
  3. Name the credential after the operator who will be allowed to fire it (e.g. NW5W) and submit.
  4. The reveal panel appears. Copy the Secret Key from the right side — the long base32 string, not the QR code. The page warns that this is the only time the value is shown.
  5. Bind the credential to the Action whose name the sender will type — e.g. unlock — via that Action’s OTP credential field with Require OTP on.

Send the Secret Key to the sender over a trusted channel.

Setting up the credential — sender side

On the sending station (the one this page is on):

  1. Open Messages in the sidebar.
  2. Open a DM thread to the receiving callsign. (Tactical, multi-recipient threads do not show the zap icon — an OTP-protected fire to many callsigns at once would be an operational footgun.)
  3. Click the zap icon (⚡) in the thread header to open the Remote Actions drawer. The drawer anchors right on desktop and slides up from the bottom on mobile.
  4. Click Manage One-Time Passwords... (under the OTP picker, or via the top-level Messages overflow menu).
  5. Click + New Secret. Give it a name that identifies the remote station — e.g. NW5W OTP.
  6. Paste the Secret Key you copied from the receiver into the Secret Key field. Whitespace is tolerated; case does not matter.
  7. Save.

The new secret now appears in the OTP picker on every macro you create against any thread.

Creating macros

A macro is a saved tile that fires a specific action against a specific remote station with a specific argument list. Macros are scoped per thread — the macros you create while the drawer is open against NW5W-9 only show up on threads to NW5W-9.

  1. Open the drawer on the target thread.
  2. Click Edit macros at the bottom of the drawer.
  3. Click + Add new macro. Fill in:
    • Label — what the tile says (e.g. unlock front).
    • Action — the action name as defined on the receiver (e.g. unlock).
    • Args — space-separated k=v pairs, or empty.
    • OTP Secret — pick the credential you saved above, or leave blank for manual OTP (you’ll be prompted to type a code at fire time, useful for actions on receivers where the operator types the code from a phone authenticator).
  4. Save. The tile appears in fire mode and is reorderable by drag.

Deleting a credential demotes its bound macros to manual-OTP rather than deleting them, so you can rotate a Secret Key without losing the macro layout.

Firing

Two ways to send a Remote Action:

  • Tap a tile. The frontend asks the backend for a fresh six-digit OTP from the bound credential, assembles @@<digits>#<action> [args], and posts it through the same send path as a hand-typed line in the thread. The outbound bubble looks identical to a normal message because it is a normal message — only the body differs.
  • Free-form sender. The drawer’s text field at the bottom lets you type an action name + args without saving a macro. Pick an OTP secret (or manual OTP), type the line, send.

The SEND button greys out when the assembled wire string would exceed the APRS frame budget (67 characters by default; 200 if you have Allow long APRS messages enabled in Preferences). Shorten args to enable the button.

A short cooldown countdown sits on each tile right after a fire — the receiver’s replay ring will reject the same OTP twice in the same 30-second TOTP step, and the cooldown is the UI’s polite reminder of that.

Reading replies

Inbound text from the same callsign within 60 seconds of an outbound fire that begins with one of these status keywords gets a zap-tagged badge in the bubble footer:

ok · error: · bad_otp · bad_arg · denied · unknown · disabled · busy · rate_limited · timeout · no_credential

Inbound text within the same 60-second window that does not begin with a status keyword stays a normal chat bubble. The trade-off is intentional: a free-form remark from the peer that happens to start with ok will be mis-badged, but unrelated chat will not be. False negatives are preferred over false positives.

Send an authenticated iGate command

Illustrated walkthrough: English (PDF) or français (PDF).

Use this procedure with the RXT iGate firmware’s Remote Command Authentication feature. In Graywolf, open Messages, select a direct conversation with the iGate, and click the lightning bolt (⚡) in the conversation header. The CA2RXU authenticated control panel is inside that drawer. You do not configure these commands on Graywolf’s Actions page.

Before the first command

The controller is Graywolf; the target is the iGate you want to control. For example, Graywolf may use N7UV-13 to control W9EN-44. These are two different fields:

WhereSetting
Graywolf: Station CallsignYour controller callsign, including SSID, for example N7UV-13.
iGate: Remote ManagementAuthorized Graywolf controller (Callsign-SSID) must contain that exact controller callsign.
Graywolf: Messages recipientThe identity the device answers to on RF: its tactical callsign when configured, otherwise its Callsign-SSID, for example W9EN-44.
Graywolf: iGate Callsign-SSID (signed identity)The iGate's Station Callsign-SSID, even when its on-air name is tactical. For example, address BURNTX but sign with N7UV.
Both devicesThe same 43-character Base64URL remote command secret, installed and saved on the iGate and stored for that target in Graywolf.

On the iGate, configure the authorized controller and install the secret in Remote Management, then save the configuration. Keep a copy of the secret for the next step. If authentication is already configured, use the existing secret; generating a different secret only on one device will not work.

Install the matching key in Graywolf

  1. Open Messages and create or select a direct conversation addressed to the device’s RF identity.
  2. Click the lightning bolt (⚡) in the conversation header. It is available in direct conversations, not tactical group conversations.
  3. Find CA2RXU authenticated control and click Install key.
  4. Set iGate Callsign-SSID (signed identity) to the Callsign - SSID field in the iGate's Station tab. Its beacon comment may end with de <Callsign>. Keep the conversation addressed to the name displayed on air.
  5. Enter a descriptive Name, paste the secret installed on that iGate into 43-character Base64URL key, then click Install. This is not the APRS-IS passcode or your Graywolf login password.
  6. Select the conversation’s send path. For a LoRa RF connection, select RF only in the conversation routing menu and select the intended LoRa TNC channel below the conversation. The TNC connection must allow transmission. If the iGate accepts management commands only via RF, an APRS-IS route cannot deliver a command it will accept.

Key installation is a one-time setup for each target. On later visits, open the same conversation and the lightning-bolt drawer; the control buttons are available without pasting the key again.

Queries and commands use different controls

What you wantHow to send it
Read the firmware versionType ?APRSV in the normal message composer and send.
Read TX or eco-mode stateType ?TX=? or ?EM=? in the normal composer. These queries require the sender to match the iGate’s managers list and obey its RF-only restriction.
Change a setting on an authenticated iGateUse one of the signed-command buttons below.

Installing an authentication key does not make Graywolf sign ordinary typed messages. For example, typing ?TX=OFF in the composer still sends an unsigned command. An iGate with authentication enabled will not execute that unsigned setting change.

ButtonSigned commandPurpose
Eco mode onEM=ONEnable eco mode, when supported by the iGate’s current operating mode.
Eco mode offEM=OFFLeave eco mode.
TX onTX=ONEnable radio transmission.
TX offTX=OFFDisable radio transmission. Graywolf asks for confirmation.
Save configCOMMITSave the current configuration for the next reboot.

Click the button for the setting you want to change. Graywolf signs the command with the saved key and a new counter, then sends it through that conversation’s route and selected channel. You do not type the signature, counter or !RC1 envelope yourself.

Queued is not applied. Graywolf’s confirmation means the APRS message entered its transmit path. Look for the iGate’s response and check the resulting setting. An APRS ACK confirms transport only; neither it nor the ordinary text reply is a cryptographically authenticated execution result.

If it does not work

  • No control buttons: check that this is a direct conversation and install the key under CA2RXU authenticated control. A TOTP Secret or a macro does not install an iGate key.
  • AUTH REQUIRED: an unsigned setting change reached the iGate from a recognized manager. Use the control button instead of the normal composer.
  • AUTH FAILED: check the matching secrets and exact controller and target Callsign-SSIDs. It can also indicate an invalid command envelope or an iGate storage error. The firmware console logs Remote command authentication rejected: ... with the precise reason. With the current RXT firmware, an already-consumed counter is ignored separately and does not produce this reply.
  • No reply: check the selected route, channel and iGate transport restrictions. A source that is not the authorized controller can be ignored without an authentication-error reply.

Changing callsigns or keys

Changing an iGate’s Station fields does not change its Remote Management settings or its secret. The published firmware verifies the signed target using its Station Callsign - SSID, even when the RF recipient is its Tactical Callsign. Address the conversation to the name displayed on air and enter the iGate's Callsign-SSID as its signed identity: for example, address BURNTX while signing for N7UV. Open Key settings, enter N7UV in iGate Callsign-SSID (signed identity), leave the secret blank and save. Changing this identity preserves the key and counter. No firmware update is required.

Without a tactical callsign, the recipient and signed target both use the Station Callsign-SSID. If that value changes, Graywolf’s saved credential target must match the new callsign. The current Key settings dialog can change the RF recipient / Destinataire RF without replacing the key or resetting the counter. Set the recipient to the on-air name and the signed identity to the Station Callsign-SSID, leave the secret blank, then save. Graywolf opens the destination conversation; check its routing policy and transmit channel before sending. Do not delete and reinstall the same key: this would reset the sender counter while the iGate still remembers it. If only Graywolf’s Station Callsign changes, update the authorized controller on the iGate; the shared secret and existing target credential can remain the same.

Graywolf keeps the key and sender counter in its configuration database. Restarting Graywolf or closing the browser does not require reinstalling the key. In Key settings, leave the secret field blank to keep the installed key and counter. A transmission failure may consume a counter; this is expected. Replacing a key resets Graywolf’s sender counter and must be coordinated with installing the same new key on the iGate.

Troubleshooting

  • bad_otp reply. The two stations’ clocks differ by more than one TOTP step (30 s). Sync NTP on both. If you just rotated the Secret Key on the receiver, update the matching secret in the sender’s credentials modal — one mistyped character produces this every time.
  • denied. The receiver’s Action has a sender allowlist that excludes your callsign. The operator on the receiver side has to add you.
  • unknown. The action name is misspelled, the Action has been deleted on the receiver, or the Action is disabled. Check the macro label vs. the Action name on the receiver.
  • bad_otp on rapid re-fire. The receiver rejects the same OTP twice within its 30-second window (replay protection). Wait for the tile’s cooldown countdown to clear and try again. Distinguishable from a mistyped Secret Key in that it only happens on the second of two fast clicks; a mistyped key fails every time.
  • SEND disabled with a tooltip. The assembled line exceeds the APRS frame budget. Shorten args or enable Allow long APRS messages on the Preferences page (200-char frames, only safe when both stations support it).
  • No zap icon on a thread. Tactical (multi- recipient) threads omit the icon by design. Open or create a DM to that callsign instead.
  • Reply has no zap badge. Either the inbound arrived more than 60 s after the fire, or its first word is not in the status-prefix allowlist. Both are normal.
